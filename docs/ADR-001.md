# ADR-001 — สถาปัตยกรรม owlcha-ledger (ย้ายจาก Google Apps Script → Vercel)

- **สถานะ:** Accepted
- **วันที่:** 2026-07-25
- **ขอบเขต:** ย้ายระบบบันทึกรายรับ-รายจ่ายร้าน Owl Cha จาก Google Apps Script (`Code.gs` + `index.html`) ขึ้น Vercel
- **ผู้ใช้งาน:** พนักงาน 5 คน

---

## 1. บริบท (Context)

ระบบเดิมเป็น Google Apps Script Web App:

- `doGet()` เสิร์ฟ `index.html`, `doPost()` + `saveData()` เขียนลง Google Sheet ชีต `ค่าใช้จ่าย` คอลัมน์ B–E
- ฝั่ง client เรียก backend ผ่าน `google.script.run` (API เฉพาะแพลตฟอร์ม Apps Script)
- สร้างรูปสรุปด้วย `html2canvas` ฝั่ง browser แล้วส่งเข้ากลุ่ม Telegram
- Google Sheet อยู่บนบัญชี **Gmail ส่วนตัว** ไม่ใช่ Google Workspace
- พนักงานทุกคน **มีสิทธิ์แก้ Google Sheet อยู่แล้ว**

**เหตุผลที่ต้องย้าย:** ต้องการ Google SSO, ควบคุมสิทธิ์เข้าใช้งานได้, และหลุดจากข้อจำกัดของ Apps Script

## 3. เหตุผลของ D3–D5 (จุดที่ถกกันมากที่สุด)

### ทำไมใช้ token ของผู้ใช้ ไม่ใช่ Service Account

พนักงานมีสิทธิ์แก้ Sheet อยู่แล้ว → การใช้ token ของเขาไม่ได้เพิ่มสิทธิ์ใหม่ให้ใคร
ผลที่ได้:

- ระบบสิทธิ์อยู่ที่เดียว (Google Sheet sharing) ไม่ต้องดูแลสองที่
- Revision history ของ Sheet บันทึกชื่อจริงของผู้แก้ → ได้ audit trail ฟรี (จึงไม่ต้องทำ D9)
- ไม่มี private key ของ Service Account เป็นความลับก้อนเดียวที่เปิด Sheet ได้ทั้งใบ

### ทำไม `drive.file` ไม่ใช่ `spreadsheets`

ตามเอกสาร Google Sheets API scopes:

| Scope | ชั้นความอ่อนไหว |
|---|---|
| `.../auth/spreadsheets` | Sensitive |
| `.../auth/spreadsheets.readonly` | Sensitive |
| `.../auth/drive.file` | **Recommended / Non-sensitive** |

ผลของการเลือก `drive.file`:

- ไม่ต้องผ่าน sensitive scope verification
- แอปเข้าถึงได้เฉพาะไฟล์ที่ผู้ใช้เลือกผ่าน Picker — ไม่ใช่ Sheet ทุกใบในไดรฟ์ของพนักงาน
- เปิดทางให้ publish เป็น Production ในอนาคตได้ (ต้องการแค่ basic app verification) เพื่อกำจัดหน้าเตือน "Google hasn't verified this app"

**ราคาที่จ่าย:** ต้องเขียนหน้าจอ Google Picker และพนักงานต้องกดเลือก Sheet 1 ครั้งต่อคน

## 4. เหตุผลของ D8 (Session policy)

Google กำหนดว่าการอนุญาตของ test user หมดอายุภายใน 7 วันนับจากการยินยอม และจะเพิกถอน refresh token
เมื่อสถานะเป็น Testing + User type External

D8 จึงถูกออกแบบให้บังคับ re-login ก่อนชนกำแพงนั้นเสมอ:

```
IDLE_MAX_SEC     =  43200  (12 ชม.)
ABSOLUTE_MAX_SEC = 432000  (5 วัน)
Google grant     = 604800  (7 วัน)

margin            = 604800 - 432000 = 172800 s = 2.00 วัน
worst case        = 432000 +  43200 = 475200 s = 5.50 วัน  < 7 วัน  ✅
```

"worst case" คือกรณีที่ absolute cap ถูกบังคับใช้ช้าที่สุดเท่าที่เป็นไปได้
(ผู้ใช้ไม่แตะแอปเลยจนเกิน 5 วัน แล้วค่อยกลับมา) — ยังอยู่ใต้ 7 วัน

**ข้อกำหนดที่ตามมา:** ต้องบังคับ `access_type=offline` + `prompt=consent` ทุกครั้งที่ล็อกอิน
มิฉะนั้น Google จะไม่ออก refresh token ตัวใหม่ในการอนุญาตครั้งถัดไป

**สำคัญ:** `session.maxAge` ของ NextAuth/Auth.js เป็น **idle timeout ไม่ใช่เพดานเด็ดขาด**
การได้ absolute cap จริงต้องฝัง `authTime` ใน JWT ตอน sign-in แล้วบังคับใช้ใน middleware

## 11. Addendum (2026-07-25 — เพิ่มระหว่างวางแผน implementation, ไม่แก้เนื้อหาตั้งต้น)

### 11.1 เหตุผลของ D11 (ลำดับแถวเมื่อแก้วันย้อนหลัง)

พนักงาน 5 คนบันทึก**คนละวันแบบหมุนเวร** (ดู OA-1) การ append ท้ายชีตจึงให้ผลเรียงตามวันที่โดยธรรมชาติ
ความไม่เรียงเกิดเฉพาะเมื่อย้อนไปแก้วันเก่า ซึ่งเป็นเหตุการณ์นาน ๆ ครั้ง และการเปลี่ยนเป็นแทรกตรงตำแหน่งเดิม
เป็นการเปลี่ยนพฤติกรรมที่ยังไม่คุ้มความเสี่ยง สิ่งที่เพิ่มแทน (ต้นทุนต่ำ): เมื่อผู้ใช้เลือกวันที่ไม่ใช่วันล่าสุดในชีต
UI แสดงคำเตือน *"คุณกำลังแก้ไขวันย้อนหลัง — รายการของวันนี้จะถูกย้ายไปอยู่ท้ายชีต"*

### 11.2 กลไกกันเขียนชนกัน (แก้ R-3): Optimistic concurrency ด้วย content hash + 409

- `GET /api/entries?date=` คืน `version` = SHA-256 ของเนื้อหาแถว (B–E) ของวันนั้น **ไม่ผสมเลขแถว**
  (เลขแถวเลื่อนได้เมื่อวันอื่นถูกแก้ → จะเกิด conflict ปลอม)
- `POST /api/entries` ต้องส่ง `baseVersion`; server อ่านซ้ำ เทียบ ไม่ตรง → **409 Conflict**
  → UI ให้ผู้ใช้เลือก "โหลดใหม่" (default) หรือ "เขียนทับ" โดยแสดงข้อมูลฝั่ง server เทียบก่อน
  **ไม่มีการเขียนทับเงียบ ๆ ทุกกรณี**

**เหตุผลของกลไกนี้:** ไม่ได้มีไว้กัน "การเขียนพร้อมกัน" แต่มีไว้กัน **stale tab บนอุปกรณ์ร่วม** —
พนักงาน A เปิดแอปบนแท็บเล็ตหน้าร้านค้างข้อมูลวันอังคารไว้ วันพุธพนักงาน B มาใช้เครื่องเดิม
กดบันทึกโดยไม่ทันสังเกต → ทับข้อมูลด้วยสถานะเก่าโดยไม่มี error ใด ๆ
**การใช้งานแบบหมุนเวรบนอุปกรณ์ร่วมทำให้ความเสี่ยงนี้สูงขึ้น ไม่ใช่ต่ำลง**
(ห้ามให้เหตุผลว่า "ความถี่ชนต่ำ" — จะชวนให้ถอดกลไกออกในอนาคต)

**Residual risk ที่ยอมรับ:** ช่องว่างระหว่าง check-then-write ภายใน request เดียวยังมีอยู่ (แคบมาก,
ไม่มี lock service ให้ใช้เพราะไม่มีฐานข้อมูล) — บันทึกไว้เป็นข้อจำกัดที่ทราบ

### 11.3 สมมติฐานการใช้งาน (Operational Assumptions)

```
OA-1  พนักงาน 5 คนบันทึกคนละวันแบบหมุนเวร ไม่มีการใช้งานซ้อนกัน
      (ยืนยันโดยเจ้าของระบบ 2026-07-25)

      ⚠️ นี่คือ "แนวปฏิบัติปัจจุบัน" ไม่ใช่ "ข้อบังคับทางเทคนิค"
         ระบบไม่ได้ป้องกันการใช้ซ้อนกัน และตัวแอปเองก็เปิดให้ทำได้
         หากรูปแบบการทำงานเปลี่ยน (เช่น 2 คนบันทึกวันเดียวกัน)
         ต้องกลับมาทบทวน D11 และกลไก optimistic concurrency ใหม่
```

### 11.4 Operational notes

- **ห้ามเปลี่ยนชื่อแท็บใน Google Sheet** — ระบบ resolve `SHEET_NAME` → `sheetId` (gid) ตอนรัน
  เปลี่ยนชื่อแท็บ = ระบบหาแท็บไม่เจอและหยุดทำงาน (แก้โดยอัปเดต env `SHEET_NAME` ให้ตรง)
- **ห้ามใส่ข้อมูลนอกคอลัมน์ B–E ในชีตนี้** — ระบบใหม่คำนวณตำแหน่ง append จากช่วง B:E เท่านั้น
  ข้อมูลในคอลัมน์ A หรือ F เป็นต้นไปจะทำให้ตำแหน่งเขียนผิด
  (สถานะจริงของชีตจะถูกตรวจยืนยันก่อนเริ่ม M3 — ถ้าพบข้อมูลนอก B:E ต้องตัดสินใจร่วมกับเจ้าของระบบก่อน)
- **CSP แบบ nonce ทำให้ทุกหน้าเป็น dynamic render** (opt out จาก static generation) —
  เป็นผลที่ตั้งใจ ไม่ใช่ regression: ทุกหน้าอยู่หลัง auth จึงเป็น dynamic โดยธรรมชาติอยู่แล้ว
  bundle budget ของหน้าแรกวัดบนพื้นฐานนี้

### 11.6 แก้ไข D4/D5 (2026-07-26): สลับ scope เป็น `spreadsheets` — ตัด Google Picker ทิ้ง

**ผู้ตัดสินใจ:** เจ้าของระบบ (หลังพบว่าเครื่ององค์กรบล็อก Google Drive ทำให้ Picker ใช้ไม่ได้
และมองว่าขั้นตอนเลือกไฟล์เป็นอุปสรรคต่อพนักงาน)

- Scope เปลี่ยนจาก `drive.file` → **`https://www.googleapis.com/auth/spreadsheets` (Sensitive)**
- ลบหน้า `/setup`, Google Picker component, และ Picker API key ออกจากระบบทั้งหมด
- **ผลที่ตามมา (trade-off ที่รับทราบแล้ว):**
  - แอปเข้าถึงชีตทุกใบใน Drive ของพนักงานได้ (ไม่ใช่เฉพาะไฟล์ที่เลือก) —
    ควบคุมด้วยการที่โค้ดอ้าง `SHEET_ID` จาก env ตัวเดียวเท่านั้น
  - ใต้สถานะ **Testing** ใช้ sensitive scope ได้โดยไม่ต้องผ่าน verification
    แต่ถ้าวันหน้าจะ publish เป็น Production ต้องผ่าน Google verification ก่อน
    (ยกระดับจาก basic เป็น sensitive verification — ทบทวน R-4 ตอนนั้น)
  - R-6 (access token ฝั่ง browser สำหรับ Picker) **ตกไป** — token ไม่ถูกส่งให้ browser อีก
  - 403/404 จาก Sheets API ตอนนี้แปลว่า "บัญชีไม่ได้ถูกแชร์ไฟล์" (พนักงานทุกคนมีสิทธิ์
    แก้ชีตอยู่แล้วตามบริบท §1 — เคสนี้จึงเกิดได้เฉพาะพนักงานใหม่ที่ยังไม่ถูกแชร์)
- **งานฝั่ง Google Cloud ที่ต้องทำตาม:** เพิ่ม scope `.../auth/spreadsheets` ใน OAuth
  consent screen, เปิด Google Sheets API, (Picker API + API key ลบทิ้งได้)

### 11.7 ขยาย data contract (2026-07-26): คอลัมน์ F = ยอดขายบนแอป (ก่อนหัก GP)

**ผู้อนุมัติ:** เจ้าของระบบ — สำหรับรายรับจากแอปเดลิเวอรี (grab/lineman/shopee)

- คอลัมน์ D ยังเก็บ **ยอดที่ร้านได้รับสุทธิ** เหมือนเดิม 100% (ไม่กระทบระบบเก่า)
- คอลัมน์ F เก็บ **ยอดขายบนแอป (ก่อนหัก GP+VAT)** — เขียนเฉพาะแถวเดลิเวอรี
  แถวอื่นเขียนค่าว่าง; UI คำนวณให้อัตโนมัติจากยอดสุทธิ (GP 30% / VAT 7% ปรับได้รายแถว)
  และผู้ใช้แก้ทับได้โดยไม่คำนวณย้อนกลับ
- version hash ของ optimistic concurrency ครอบคลุม F ด้วย (แก้ F อย่างเดียวก็ถือว่า conflict)
- Apps Script เดิมอ่านแค่ B–E → ไม่พังระหว่างรันขนาน แต่แถวที่ระบบเก่าเขียนจะไม่มีค่า F
- ⚠️ หัวคอลัมน์ F ในชีตปัจจุบันเขียนว่า "ประเภทรายการ" — เจ้าของระบบควรแก้หัวเป็น
  "ยอดขายบนแอป" ให้ตรงความหมาย (ระบบไม่แตะแถวหัวตาราง)
- หมายเหตุ: ข้อจำกัด N10 คงเดิม — ห้ามมีข้อมูลในคอลัมน์ A หรือ G เป็นต้นไป
